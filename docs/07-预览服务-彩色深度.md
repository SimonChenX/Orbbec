## 1. 它是什么

一个单文件 Python 服务（`viewer.py`，仅用标准库 + numpy + PIL）：

| 流 | 来源 | 实现 |
|---|---|---|
| 彩色 | `/dev/video0`（标准 UVC） | `ffmpeg` 读 MJPEG → **0° 时原生透传**（`-c:v copy`） |
| 深度 | Orbbec SDK v1（私有协议，无 video 节点） | `ctypes` 直调 `libOrbbecSDK.so`，零编译 |

两路都用「最新帧槽」（`Feed`）发布，HTTP 端以 `multipart/x-mixed-replace` 推给浏览器，
**慢客户端自动丢帧**，不会拖慢采集。

### 端点

| 路径 | 说明 |
|---|---|
| `/` | 800x480 全屏 kiosk 页面（双画面 + 状态栏） |
| `/color.mjpg` `/depth.mjpg` | 两路 MJPEG 流 |
| `/snapshot/color.jpg` `/snapshot/depth.jpg` | 单帧快照（排障取证用） |
| `/api/status` | JSON 状态：`ok` / `boot` / 每路 `state,fps,seq,clients,meta` |

## 4. ⚠️ 本服务踩过的两个坑（重要）

### 坑 A：Chromium 对 MJPEG 断流**不报错**，画面静默冻死

**现象**：页面时钟、底部数字照常在动，**两个画面却完全静止**（用户报「屏幕卡死了」）。

**根因**：`multipart/x-mixed-replace` 的 `<img>` 连接被服务端切断时，
Chromium **通常不触发 `img.onerror`**，只是把最后一帧留在屏幕上。
所以服务一重启（部署、改配置都会重启），kiosk 画面就永久冻住 —— 除非人工刷新页面。

**处理**：`web/app.js` 里加了三层自愈，任一层命中就重建连接：

1. **画面活性探针**（唯一可靠的一层）：把 `<img>` 画进 64x36 的小 canvas 取哈希，
   连续 6 秒哈希不变 → 重连。**直接测「看到的东西有没有在变」，不会漏判。**
   （相机噪声保证静止画面每帧哈希也不同，实测 4 帧无一相同，不误报。）
2. **服务启动标识 `boot`**：`/api/status` 暴露进程启动标识，服务一重启 → 立即重连。
3. **帧号看门狗 `seq`**：服务活着但不再出帧时兜底。

> ⚠️ **只靠 `seq` 会漏判**：服务重启后 `seq` 从 0 重新计数，浏览器看到「帧号在变」会误判为正常。
> 这是第一版看门狗失败的原因，必须配合 `boot` 或画面探针。

**验证方法**（可复现）：`systemctl restart ob-viewer` → 等 15 秒 → 隔 5 秒截两张屏，
比较两画面区域的变化像素占比；>2% 即已自愈。

### 坑 B：`pkill -f` 会杀掉自己的 SSH 会话

**现象**：远程执行 `pkill -f "dashboard-kiosk"` 时 SSH 直接断开（exit 255）。

**根因**：`pkill -f` 匹配**整条命令行**，而你的 SSH 命令行里就含有这个字符串。

**处理**：用字符类打断自匹配 —— `pkill -f "dashboard[-]kiosk"`。

## 5. 性能调优记录（树莓派 4，4 核）

### 5.1 先给结论：CPU 花在哪

| 配置 | 系统空闲 | 说明 |
|---|---|---|
| 彩色 720p / 深度 640x480 / 深度渲染 30 上限（**初版**） | **7%** ❌ | 用户报「CPU 占满」 |
| 彩色 640x480 / 深度 **320x240** / 30（**定稿**） | **~50%** ✅ | 参见下表各项 |

定稿时的进程分布（`top` 实测）：

| 进程 | CPU | 是什么 |
|---|---|---|
| chromium（kiosk 浏览器，合计 4 个进程） | **~133%** | 与流分辨率**无关**，正比于「每秒画面更新次数」 |
| python3（ob-viewer） | **~54%** | 深度链路（SDK 深度引擎 + 渲染 + HTTP） |
| 其余（BT-Panel/rustdesk/hermes/labwc…） | ~20% | 与本服务无关 |

对照实验（**重要，别再重走**）：

| 实验 | 结果 |
|---|---|
| 把 viewer 停掉、画面冻结 | chromium 仍 **132%** → 视频更新不是它的大头 |
| kiosk 切到**日历页**（静态） | chromium **45%**、系统空闲 **88.9%** |
| kiosk 切回相机页 | chromium **133%**、系统空闲 **48%** |
| 彩色 640/480/320/352x288 各档对比 | chromium 几乎不变 → **不吃分辨率** |
| 彩色 30+深度 30 / 彩色 30+深度 10 / 彩色 15+深度 10 | chromium 133 / 124 / 122% |

→ **结论**：Chromium 的开销是「**每次画面更新的固定成本 × 更新频率**」（约 1.3~1.8% CPU 每次/秒，
即每次更新 ~13-18ms：JPEG 解码 + 纹理上传 + 合成 + 呈现）。与图像大小、码率无关。
所以想再降只有两条路：**降更新频率**（彩色 15fps 可省 ~25% 一个核）或换渲染方式。
给 `<img>` 加 `transform:translateZ(0)` 提升为独立合成层（已加）收益很小。

> 若哪天嫌 CPU 高：把 `OB_COLOR_FPS` 改 15 是收益最大的一刀（但需求方要的是 30fps）。

### 5.2 ⭐ 深度分辨率 640x480 → 320x240：**收益最大的一刀**

深度引擎（`libdepthengine.so`）是**按流分辨率**计算深度的，所以 640x480@30
光引擎本身就吃掉一个多核。设备侧 640x480 **只提供 @30**（没有 15fps 档），
所以「降渲染帧率」治标，「**降流分辨率**」才治本：

```bash
OB_DEPTH_SIZE=320x240     # 引擎工作量 → 1/4
OB_DEPTH_FPS=30
```

实测：ob-viewer 进程 **135% → 54%**，系统空闲 **7% → 54%**。
屏上面板只有 376px 宽，320x240 放上去看不出差别。

### 5.3 彩色：0° 时**原生透传**，别重编码

| 项 | 优化前 | 优化后 | 做法 |
|---|---|---|---|
| 彩色 | 25 fps（ffmpeg 占 92% CPU） | **30.0 fps**（几乎不占 CPU） | 0° 时 `-c:v copy` 原生透传，去掉无谓的重编码 |
| 深度渲染 | 28.7ms/帧 | **11.7ms/帧** | 伪彩改走 PIL **调色板（P 模式）**，把上色交给 C 层 |

深度渲染耗时构成（Pi4 实测，640x480）：

| 步骤 | 耗时 |
|---|---|
| numpy 数组管线（raw → RGB） | 28.7ms（优化前的大头） |
| └ 其中 `LUT[idx]` 花式索引 | 11.2ms |
| └ 其中 `rgb[~valid] = 0` 掩码赋值 | 5.9ms |
| **调色板路径（现用）** | **11.7ms** |

做法：`idx = clip((arr-rlo)*254/(rhi-rlo)) + 1`（**索引 0 保留给无效像素 = 黑**）
→ `Image.fromarray(idx, "P")` + `putpalette(PAL)` → `convert("RGB")` → 存 JPEG。
输出字节数几乎一致（26107 vs 26103），**画质无损失**。

> 顺带结论：Pillow 已链接 **libjpeg-turbo**（`features.check("libjpeg_turbo") == True`），
> JPEG 编码本身只要 ~5ms，**不是**瓶颈，不必去折腾编码器。

### 5.4 排障小抄：怎么量 CPU

```bash
top -bn1 | grep "%Cpu"                                  # 瞬时总体（看 id 空闲率）
ps -eo pcpu,comm --sort=-pcpu --no-headers | head       # 进程（注意是生命周期均值）
python3 scripts/thrcpu.py <pid> 6                          # ★ 按线程实测（读 /proc/PID/task/*/stat 求差）
```

`scripts/thrcpu.py` 的关键：**读两次 `/proc/<pid>/task/<tid>/stat` 的 utime+stime 求差**再除以采样秒数——
`top`/`ps` 给的是生命周期均值，在多线程 Python 里会把真正的热点线程平均掉，看不出来。

## 6. 复现步骤（从零到画面）

```bash
# 1) 装到目标机
tar czf - viewer | ssh root@<pi> 'tar xzf - -C /opt/orbbec && sh /opt/orbbec/viewer/deploy/install.sh'

# 2) 起服务
systemctl restart ob-viewer && systemctl is-active ob-viewer

# 3) 看状态（两路都应 state=ok）
curl -s http://127.0.0.1:8790/api/status

# 4) 实测帧率（注意：不能用 ffmpeg -t 计时，MJPEG 无时间戳，ffmpeg 按默认 25fps 时间基算，量不准）
python3 /tmp/measure_fps.py        # 墙钟计数脚本，见下

# 5) 切到相机屏
sh /opt/orbbec/viewer/deploy/switch-kiosk.sh camera
```

`measure_fps.py` 的要点：用 `urllib` 按**墙钟时间**读 N 秒，累计收到的 `\xff\xd8\xff`（JPEG 帧头）个数，
再除以实际耗时 —— 这才是真实 fps。
